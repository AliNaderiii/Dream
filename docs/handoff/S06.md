### 0b. The scheduler flake is pinned

`tests/test_scheduler.py::test_start_and_stop_are_clean` failed once on main
CI (run 32252554954, Python 3.12): `assert 2 == 1`, the same schedule id
fired twice.

**Root cause (a race, not an S05 regression):** the due job uses cron
`*/1 * * * *`. `mark_executed` sets `next_run` to the next minute boundary
*after now*; when the first tick lands just before a boundary (e.g.
`XX:XX:59.95`), the new `next_run` is only ~50 ms away, and another tick
inside the test's 0.12 s sleep window legitimately fires the *next*
occurrence. The daemon behaved correctly; the test depended on wall-clock
luck.

**Fix (test pin, the preferred option):** the due job is created with
`max_runs=1`, so after the first execution it is exhausted and disabled —
a second fire is impossible regardless of where the clock lands. The test
still proves what it always claimed: the loop starts (fires once), and
`stop()` is clean (`running is False`). The daemon itself was left alone;
`tick()` already advances `next_run` before running, and `_loop` serialises
ticks, so there is no in-flight overlap to close.

**Proof:** `python -m pytest tests/test_scheduler.py -q` run **twice** —
130 passed each run — plus 6 consecutive targeted runs of the pinned test.

### 1. Projects — folders, not a fake CRM

`apps/desktop/src/routes/projects.tsx` is a working screen (the EmptyState
placeholder is gone):

- **Create**: name + optional workspace folder. Under Tauri the folder comes
  from the native picker (`dialogApi.selectFolder`, the existing
  "choose workspace" pattern); in the browser the path is typed. The folder
  is linked **in place** — nothing is copied.
- **Session grouping**: every project lists its sessions (open → `/chat/:id`,
  remove → back to the ungrouped list). The add-picker offers only sessions
  no project claims; a session belongs to **one** project — adding it
  somewhere lifts it out of anywhere else. "New session here" creates and
  groups one, then navigates to it.
- **Delete with confirm**: `ConfirmDialog` states that sessions are kept;
  deleting a project ungroups, never destroys.
- **Backend**: seven new RPCs appended at the END of `BridgeMethods` —
  `project.create/list/get/update/delete/add_session/remove_session` — with
  the sessions-index persistence rules (`data/bridge_projects.json`,
  override `DREAM_PROJECTS_PATH`, best-effort atomic writes, restart-safe).
  No memory-schema change, so no migration was needed.
- **Echo runtime**: `EchoProjectsRuntime` mirrors the sidecar contract
  (validation errors, one-project-per-session, delete-ungroups) so browser
  dev and vitest exercise the full flow; it only groups sessions the echo
  transport actually knows.

### 2. Scheduler UI — the built engine, exposed at last

`apps/desktop/src/routes/scheduler.tsx` (lazy route, activity-rail entry with
the AlarmClock icon) surfaces `dream/scheduler.py` + `dream/cron.py` +
`dream/nl_schedule.py` through the RPCs that already existed (no backend
change for the CRUD surface):

- **List**: name, human description (`human`), cron expression, next run in
  the document locale **and Jalali** (`Intl` `fa-IR-u-ca-persian`), last run,
  run count, badges for approval-required / paused / finished.
- **Create from Persian/English prose**: live `schedule.preview` (debounced)
  shows the human reading, the cron, and the next run in both calendars.
  Prose is re-parsed by the sidecar on submit — its verdict wins.
- **Toggle, run-now, history** (per-job run rows with status badges),
  **delete with confirm**.
- **Approval, fail-closed**: a "Require approval before each run" switch on
  the form; approval-gated jobs are badged; run-now on a gated job does not
  block the UI — the run registers in the new **approval queue** panel
  (`approval.list`, a new read-only RPC appended to `BridgeMethods`), where a
  human approves or denies via `schedule.approve`. Nobody to ask, timeout, or
  denial → `approval_denied` (gate G11 semantics, unchanged). In echo mode
  there is no approver, so a gated run-now is denied immediately — the
  fail-closed default is visible in the browser.
