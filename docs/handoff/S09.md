# S09 — Aval AI as the recommended Iranian cloud path

**Status: Gate G9 met.** Aval AI is now a first-class provider row and a named
router route (`aval`) with honest leave-the-machine sentences, without cloning
any vendor and without probing the network. Official OpenAI / Anthropic /
Google cards remain in the catalog as optional extras; the local unlimited plan
and the offline demo are unchanged.

## What changed

### Catalog (`dream/model_providers.py`)

- New first row `avalai` in `PROVIDER_CATALOG`:
  - `name: "Aval AI"`, `website: https://chat.avalai.ir/platform/home`,
    `docs: https://docs.avalai.ir`
  - `auth_type: "api_key"`, `endpoint: https://api.avalai.ir/v1`,
    `model_list_url: https://api.avalai.ir/v1/models`, `supports_streaming: true`
  - `default_models: ["gpt-5.6-sol", "gpt-5.6-luna", "claude-sonnet-5", "gemini-3.7-flash"]`
    — every id is taken from the Aval docs model explorer
    (docs.avalai.ir/en/models/index) and the quickstart; none are invented.
    DeepSeek `deepseek-chat`/`deepseek-reasoner` were retired by Aval on
    2026-07-24 (docs.avalai.ir/en/deprecations), so no DeepSeek id is listed.
  - Aval's documented fallback host `https://api.avalapis.ir/v1` is recognised
    by the router for routing but is never probed.

### Environment (`.env.example`)

- New commented `# AVALAI_API_KEY=` documented with the Aval story. The name is
  read via a literal `os.environ.get("AVALAI_API_KEY")` in `dream/router.py`,
  satisfying repo rule M23 (`tests/test_m23_env_example_names.py` now also
  pins `AVALAI_API_KEY` in the known-read set).
- The key is never logged; the desktop stores it through the existing keychain
  path (`KeychainCredentialStore`) when the Aval card is added.

### Router (`dream/router.py`)

- New named route `aval`:
  - `leaves_machine = True`
  - English sentence: *"Route: aval — this turn is sent to Aval AI
    (api.avalai.ir), the Iranian cloud provider you configured; your message
    leaves this machine."*
  - Persian sentence (written as `\u` escapes per M16): the same meaning —
    the turn is sent to Aval AI (api.avalai.ir) and the message leaves this
    machine.
- Detection (deterministic, never a network probe): `AVALAI_API_KEY` set, or
  `OPENAI_BASE_URL` on `api.avalai.ir` / `api.avalapis.ir` (trailing slash and
  case-insensitive, lookalikes stay BYOK), or `DREAM_BACKEND=aval` / `avalai`.
- Priority when no explicit session pick: explicit `DREAM_BACKEND` → hosted
  (official base + key) → `aval` (Aval key/base) → Ollama → other BYOK → echo.
  An official key with the official (or default) base still beats an Aval key;
  an `OPENAI_API_KEY` pointed at an Aval base is honestly named `aval`.
  `DREAM_HOSTED_BASE_URL` is not wired anywhere in the repo, so it was not
  invented.
- `_ROUTE_BACKEND["aval"] = "openai"` — Aval is OpenAI-compatible, so
  `build_router_backend()` builds the same client the hosted/byok routes use.
- `dream --route` and `/route` print the new name and both sentences;
  `route.resolve` surfaces them unchanged in shape (`name`, `leaves_machine`,
  `sentence_en`, `sentence_fa`) — no new DTO field was needed.

### Bridge (`dream/bridge/methods.py` — one append)

- `build_configured_backend` now treats kind `avalai` as OpenAI-compatible.
  Without this single append, an Aval card added from the catalog would have
  silently fallen through to the echo default — the honest route would have
  said "aval" while the backend answered as echo. The change is one word in
  the existing OpenAI-compatible kinds set.

### Desktop (catalog ordering + i18n only)

- `avalai` is the first catalog row, so the Providers page "Add provider"
  default and the catalog dropdown start with Aval AI — Aval first in the
  recommended ordering; no page redesign.
- `ProviderKind` in `apps/desktop/src/types/index.ts` gained `'avalai'`.
- `RouteDto.name` in `apps/desktop/src/lib/bridge/types.ts` gained `'aval'`;
  the billing summary's `routeNameKey` maps `aval` to a new `billing.routeAval`
  label instead of dishonestly falling back to "Offline echo".
- Locale changes went through `generate-locales.mjs` only (8 identical key
  trees): new `settings.billing.routeAval` and an Aval-first
  `providers.connectFirstDesc` in all 8 languages, then regenerated.
- `npm run format`, `npm run format:check`, and `npx tsc --noEmit` are green.

### Docs

- `README.md` and `docs/PRODUCT.md`: one short Aval sentence in the Iranian
  users section and the updated routing priority (`hosted → Aval → Ollama →
  BYOK → echo`).
- `docs/bridge/protocol.md`: `route.resolve` name union includes `aval`; the
  `provider.*` section documents the `avalai` catalog row and the no-live-probe
  rule.

## Tests (offline only)

- `tests/test_router.py`: Aval key / Aval base spellings / explicit
  `DREAM_BACKEND=aval|avalai` select `aval`; official key + official base stays
  `hosted` even with an Aval key; Aval outranks Ollama; Ollama still beats
  unnamed BYOK; demo/echo stays `leaves_machine False`; lookalike Aval URLs are
  BYOK not `aval`; a `urlopen` monkeypatch proves route resolution never opens
  a connection. Route-name pin updated to the five documented names.
- `tests/test_model_providers.py`: catalog set includes `avalai`; the entry's
  fields and docs-sourced default models are pinned; an `avalai` card is never
  reported `local`.
- `tests/test_bridge_commerce_route.py`: `route.resolve` returns the `aval`
  route when `AVALAI_API_KEY` is set.
- `tests/test_m23_env_example_names.py`: `AVALAI_API_KEY` in the known-read
  set.
- No test performs a live HTTP call to `avalai.ir` (or anywhere else): all
  provider discovery/probe tests use injected fake openers, and the router has
  no network code at all.
