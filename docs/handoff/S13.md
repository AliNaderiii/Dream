# S13 — Desktop launch must work (hotfix + shell craft)

**Date:** 2026-08-20

**Author:** Ali Naderi <alinaderi@users.noreply.github.com>

## Goal

The owner installed `Dream_0.3.0_x64-setup.exe` and the window crashed seconds
later with the in-app error boundary:

```
Cannot read properties of undefined (reading 'dot')
```

A console-like (`cmd`) window also opened and closed in a loop. The owner wants
to **use the desktop app** — that is the product. This session hotfixes the
crash, stops the console flashing, makes the "kernel missing" state honest in
EN + FA, and gives the shell a calmer disconnected empty-state — without scope
creep (no Zarinpal, Telegram/Bale/Eitaa, council auto-start, agent-loop
rewrite, commerce prices, CPython bundle, Authenticode, or macOS signing).

## Root causes (verified in source)

1. **UI crash.** `ConnectionState` in
   `apps/desktop/src-tauri/src/bridge/state.rs` is serialised with
   `rename_all = "lowercase"`, so `set_state`/`restart()` emit the enum
   **directly** as a bare JSON string (`"restarting"`, `"connecting"`, …).
   The frontend `TauriBridgeTransport::wireState` in
   `apps/desktop/src/lib/bridge/client.ts` did
   `handler(payload.state)` — reading `.state` off a **string**, which is
   `undefined`. `BridgeStatusIndicator` then read `STATE_META[state].dot` →
   `undefined.dot` → the owner screenshot. `BridgeConnectionState` also had no
   `'restarting'` member, so even a `{ state: "restarting" }` envelope would
   have fallen through `STATE_META`.
2. **Flashing consoles.** `process.rs` `spawn` used `stderr(Stdio::inherit())`
   and no `CREATE_NO_WINDOW`, so each failed `python`/`py`/`python3` discovery
   attempt could flash a console — worse with the Windows Store `python` stub.
